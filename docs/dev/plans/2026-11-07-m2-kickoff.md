- 작성일: 2026-11-07 · 11/7 배치 T4-1(AC-6)
- 기준 문서: [로드맵 SPEC](../../specs/2026-09-14-rustra-roadmap.md) §4.2(S1~S7)·§M2(G2), [로드맵 상태 원장](../../verification/2026-09-16-roadmap-status.md) §4, [11/7 배치 계획](2026-11-07-next-steps-batch.md) T4
- 기준 상태: main `b7c07503` + working tree. 발행 라인 패키지: `cli`/`types 0.13.0`, `node`/`bun 0.11.1`, `react-native 0.11.0`, `react 0.8.4`, `tauri 0.10.1`(독립 버전 정책).
- **상태: 기준·프로토콜 확정. 소비자 앱 선정은 사용자 결정 대기다.** 본 문서는 선정하지 않는다 — 선정 기준, 후보 조건, A5/A6 절차, 기록 양식만 정한다.

## 1. 목적과 경계

M2(G2)는 대표 소비자 2개에서 설치 이후의 실제 사용을 검증하는 단계다. 그 앞에 필요한 결정(소비자 앱 선정)과 절차(A5 업그레이드/롤백, A6 외부 평가자)·기록 계약을 미리 확정해서, 사용자가 소비자 앱을 선정하는 즉시 검증이 일정·절차 논의 없이 착수되도록 한다.

본 문서가 하지 않는 것:

- 소비자 앱 선정·평가자 모집 채널 선택 — 각각 사용자 결정 사항이다(§2·§4, 그리고 [배치 계획](2026-11-07-next-steps-batch.md)의 사용자 결정 대기 목록 ①·②).
- 실제 검증 수행 — 4주 사용 기록, 생명주기 100회, 2시간 부하는 선정 뒤 실행이다.
- 로드맵 요건의 변경 — 4주·100회·2시간·연속 2회 업그레이드 등 수치는 SPEC 그대로 유지하며 본 문서는 재구성만 한다. 완화가 필요하면 먼저 SPEC을 고친다(SPEC §8 관례).

본 문서 작성은 M2/G2 착수가 아니라 착수 준비 완료를 뜻한다. 선정 전까지 M2는 미착수 상태로 기록한다([상태 원장](../../verification/2026-09-16-roadmap-status.md) 2026-11-07 라운드).

## 2. 소비자 앱 선정 기준 (사용자 결정 대기)

### 2.1 필수 조건 (SPEC §M2·S5 준수)

1. **비계산기** — calculator 예제의 이름만 바꾼 사례로 채울 수 없다(SPEC §M2 명시).
2. **목적·사용 흐름 상이** — 두 앱이 서로 다른 문제를 푼다. 같은 유형의 도구 두 개로 채우지 않는다.
3. **동일 계약 2호스트** — 최소 한 앱이 동일 Rust 계약을 기존 호스트 2개에서 사용한다(예: Tauri 데스크톱 + RN 모바일). 이 조건이 계약 재사용(제품 설명의 중심 문장)을 실사용에서 증명한다.
4. **기존 앱** — 새 템플릿이 아니라 실제로 존재하고 사용 중인 앱이어야 한다. A5의 업그레이드/롤백과 4주 사용 기록이 의미를 갖려면 실제 변경·배포 이력이 있어야 한다(SPEC §M1 "기존 앱 연결은 새 템플릿 성공으로 대체하지 않는다"와 같은 논리).
5. **흐름 다양성** — 최소 한 흐름은 명령·이벤트·실패·취소·종료를 함께 사용한다(SPEC §M2).
6. **접근성** — 소비자 저장소 읽기·검증 브랜치 작성 권한, 그리고 검증 기기(Tauri/macOS 실제 창, RN Android·iOS 실기기) 접근이 가능해야 한다. iOS 실기기가 없으면 해당 인증은 미완료로 남는다(SPEC §M2 종결 문단 — desktop/Android 작업은 막히지 않는다).

1. 후보 조사 — 위 표에 조건별 충족 여부와 함께 기록한다.

3. 선정 직후 §6의 착수 순서로 진입한다.

## 3. A5 업그레이드/롤백 프로토콜 (기존 앱 Tauri 1 + RN 1)

요건 재인용([상태 원장](../../verification/2026-09-16-roadmap-status.md) §4 M1-A5): 현재 Rust 패치 왕복에 이어 **Tauri 기존 앱 1개와 RN 기존 앱 1개**에서 JS·crate·생성물·native artifact를 묶어 업그레이드/한 단계 rollback한다. 소비자 저장소가 정해진 뒤 해당 저장소 범위에서 수행한다. SPEC G1의 계약도 유지한다 — 업그레이드·롤백은 공개 레지스트리 배포물로 수행하며, 기존 패키지 버전 숫자의 강제 통일은 요구하지 않는다(독립 버전 정책).

절차(각 앱 공통):

1. **사전 보존** — 현재 정상 버전 조합(JS 패키지 정확 핀, Rust crate 버전, 생성물 해시, native artifact 해시)과 복원 경로(직전 배포물·롤백 스텝)를 먼저 기록·보존한다(원장 §4 M2 첫 머리글과 같은 순서).
2. **업그레이드** — JS·crate·생성물·native artifact를 다음 발행 라인으로 **한 묶음으로** 올린다. codegen 재생성과 네이티브 재빌드를 포함하고, 부분 업그레이드로 계약 해시 불일치 상태를 만들지 않는다(S4 계약).
3. **검증** — 대표 업무 호출, 이벤트 수신·해지, 계약 해시 일치, (RN) 네이티브 모듈 정상 적재를 실행으로 확인한다.
4. **한 단계 롤백** — 직전 정상 조합으로 되돌리고 3과 같은 검증을 반복한다. 생성물·native artifact도 롤백 대상이다(생성물만 새 버전에 두는 부분 롤백 금지).
5. **기록** — §5.1 사용 기록의 업그레이드 전후/롤백 결과 열에 남긴다.

주의:

- **연속 2회 업그레이드**(S7·G2)는 서로 다른 발행 라인 2개에 대해 이 절차를 반복하는 것으로 채운다. 같은 라인 재실행·되돌리기 반복으로 대체하지 않는다.
- **RN 앱의 이벤트 검증 전제** — RN 이벤트 푸시 교착 수정은 구현 완료·발행 대기다(원장 2026-11-07 라운드). 수정이 발행 라인에 반영되기 전에는 RN 앱의 이벤트 수신 검증을 미완료로 기록하고, 반영 뒤 rn-android 여정 `--assert-events` 재검증과 연결한다.
- Rust 패치 왕복(baseline→candidate→rollback)은 이미 자동 여정으로 증명됐다(원장 §0). A5는 그 절차의 '기존 앱' 확장이며, 자동 여정 성공으로 대체하지 않는다.
- 소비자 앱 전용 도메인 로직은 소비자 저장소에 남긴다(SPEC §4.2). 업그레이드 과정에서 발견한 공통 브릿지 결함만 최소 재현과 함께 Rustra 개선 대상으로 가져온다.

## 4. A6 외부 평가자 프로토콜 (모집 채널 = 사용자 결정, 미선정)

- **평가자 정의**(SPEC §4.1 A6): Rust와 해당 JS 호스트를 사용할 수 있으나 Rustra 개발에 참여하지 않은 사람.
- **구성·수용 기준**: 평가자 5명 중 Tauri 최소 1명, RN Android 최소 1명, RN iOS 최소 1명을 포함하고, 첫 호출 성공 4명 이상. 개입 단계·해결·준비된 환경 시간·전체 시간을 기록한다.
- **모집/연락 채널: 사용자 결정 사항 — 현재 미선정.** 연락 권한도 사용자가 부여해야 한다(원장 §4 A6·SPEC §4.1). 채널이 정해지기 전까지 A6는 미착수로 둔다. 본 문서는 채널을 특정하지 않는다.
- **평가자에게 제공하는 것**: 모든 평가자에게 **같은 문서 경로**만 제공한다 — [공개 레지스트리 도입 검증](../../registry-onboarding.ko.md)(EN/KO). 유지보수자의 개별 개입 없이 시작하게 하며, 도움 요청이 들어오면 그 단계를 기록한 뒤 개입한다.
- **시간 목표의 해석**: 첫 성공 시간 제안 목표(준비된 Node/Bun 환경 15분, 준비된 Tauri/RN 환경 30분 이내)는 미측정 제안 목표다. SDK 설치·다운로드 대기는 별도 열로 분리 기록하고 전체 경과 시간도 함께 남긴다(SPEC §4.1).

기록 최소 열 — [상태 원장](../../verification/2026-09-16-roadmap-status.md) §4에서 재인용(원문 유지):

평가자 관측 없이 성공률이나 첫 성공 시간을 추정하지 않는다. 초기 5명 표본은 개선 판단용이며 시장 성공률 추정치가 아니다(SPEC §4.1).

## 5. M2 기록 양식 (G2 증거 계약)

### 5.1 사용 기록 (소비자별 4주 + 연속 2회 업그레이드)

최소 열 — 원장 §4 M2에서 재인용(원문 유지):

> 소비자/commit/package/artifact 식별자, 날짜·실행 시간, 주요 업무 횟수, 호스트·기기·OS, 기대/실제 결과, 실패와 재현 절차, 수정 버전, 업그레이드 전후/rollback 결과.

- 관찰 기간의 시작은 실제 검증 실행일로 한다. 날짜 경과만으로 완료하지 않는다.
- 연속 2회 배포 업그레이드 완료(§3 절차 2회)를 같은 기록에서 추적한다.
- 매 기록에 요구사항 ID(S1~S7 중 무엇의 근거인지)·후보 SHA/버전·측정 시각을 붙인다(SPEC §6 증거 운영).

| 소비자/commit/package/artifact | 날짜·실행 시간 | 주요 업무 횟수 | 호스트·기기·OS | 기대/실제 결과 | 실패·재현 절차 | 수정 버전 | 업그레이드 전후/롤백 결과 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| (선정 후 기입) | | | | | | | |

### 5.2 생명주기 100회 레시피

- **Tauri/macOS**: 실제 창의 생성→탐색→닫기를 반복한다(실제 WebView — 헤드리스 대체 불가).
- **RN/Android·RN/iOS 실기기**: 전경↔배경 전환, reload, 종료를 반복한다. 시뮬레이터 실행은 별도 표기하며 실기기 인증을 대체하지 않는다.
- **1회 반복의 정의**: 창/앱 시작 → 대표 업무 1회(명령 1·이벤트 수신 1 포함) → 구독·pending 정리 → 종료. 소비자별 업무 흐름 문서(착수 후 §6 3단계 산출물)에 카운터 산정 방식을 먼저 명시한다.
- **판정(100회)**: 중복 전달 0, 종료 후 호출 반영 0, unhandled 오류 0. 예상된 취소·타임아웃은 결함에서 분리해 별도 집계한다(기록은 남긴다).
- **전제**: RN의 이벤트 수신 단계는 교착 수정 발행 라인에서만 유효하다(§3 주의 참조). 수정 전 라인으로 실행하면 그 조건을 기록에 명시한다.

### 5.3 조합별 2시간 부하 레시피

- **조합 정의**: 소비자 × 호스트 × 기기(예: 소비자 A × Tauri/macOS, 소비자 B × RN/Android 실기기). 조합별로 각각 실행한다.
- **레시피**: (1) warm-up 구간 — 길이와 제외 집계 기준을 먼저 명시, (2) 2시간 연속 대표 부하 — 소비자 실제 업무 기반의 명령·이벤트·채널 혼합, (3) 종료 후 정리 — 구독 해지·pending 취소·엔진 종료.
- **기록**: RSS 시계열(실제 프로세스·기기 측정값 — 파일 크기 합 금지, SPEC §4.3 측정 규칙), pending/channel/subscription의 기준값과 정리 후 값, 예상 취소·타임아웃의 분리 기록.
- **판정**: 채널·구독·pending 호출이 정리 후 기준값으로 돌아오고, warm-up 뒤 RSS 증가 추세가 설명되지 않은 채 남지 않는다.
- 2시간 실행과 4주 사용 기록은 서로 대체하지 않는다(원장 §4 M2).

### 5.4 오류·계약 결함 기록

- 오버로드·잘못된 입력·계약 불일치 입력에서 데이터 손상이나 조용한 성공이 없다. 복구·재시도 여부가 오류 계약과 일치하는지 확인한다(G2).
- 소비자에서 발견한 공통 브릿지 결함만 최소 재현과 함께 Rustra 개선 대상으로 가져오고, 재현 절차·영향 버전을 이 양식의 실패 열에 남긴다.
